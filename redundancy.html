第 02 章 · 冗余

冗余与故障转移：主备、多活与脑裂

冗余是高可用的核心思想：用额外的副本换取故障时的接管能力。但“多一台机器”并不等于高可用——主备与多活的根本差别，不在机器数量，而在同一时刻有多少个写入者，以及故障发生时谁来判定、谁来接管。

阅读约 18 分钟 关键词：主备 · 多活 · RTO / RPO · fencing · 单元化
本章要点
  • 主备是单写入者模型：任何时刻只有一个写入者，故障时转移写入权。
  • RTO 主要耗在检测与判定；RPO 由同步或异步复制决定，两者不可兼得。
  • 没有 fencing 的主备会在网络分区时出现双主，仲裁、租约或 STONITH 是必需项。
  • 多活的本质是并发写问题；工程主流是“单元化 + 异步复制”，不是任意多写。

冗余的层次：从机器到机房

冗余可以发生在很多层次：进程、机器、机架、可用区、机房、地域。层次越高，隔离的故障越大，成本也越高。同一机架上的两台服务器可以防进程崩溃和单机硬件故障，却无法防机架掉电；同城两个机房可以防火灾，却无法防城市级灾害。

设计冗余时先画故障域：哪些组件会一起故障？共享电源、共享交换机、共享配置中心、共享发布流程，都会把“两个副本”变回“一个故障域”。冗余的数量不是关键，故障域是否真正隔离才是关键。

重点冗余的有效性取决于故障域是否隔离。两台机器共享电源、交换机或配置，本质上仍是一个故障域；备份能恢复数据，但不等于能快速接管服务。

主备：单写入者模型

主备 · active-passive

A 对外服务，B 是与 A 硬件、环境、部署完全一致的备用节点，持续复制数据但不对外服务。A 发生故障时，将写入权转移至 B。冷备、温备、热备的区别，在于备机的就绪程度。

多活 · active-active

A、B、C 同时对外服务并接受写入。单个节点故障不会中断服务，但多个节点同时修改同一条数据时，必须解决写入冲突。

RTO ≈ 30–60s（示意）

点击“模拟主节点故障”，观察一次完整切换。

从演练台可以看到，主备切换不是一次瞬时动作，而是“检测 → 判定 → 提升 → 切流”的连续过程。RTO 主要消耗在前两步：检测要等心跳超时，判定要避免网络抖动导致误切；真正提升备机和切换 VIP 反而很快。因此缩短 RTO 的关键，是设计可靠的故障检测与仲裁机制，而不是单纯提高机器性能。

RPO 则由复制方式决定。同步复制要求主库等待备库确认，故障时数据不丢，但写入延迟上升；异步复制先返回客户端，性能更好，故障瞬间可能丢失尚未复制的那一段写入。选择哪一种，取决于业务能否接受数据缺失。

重点RTO 主要卡在“检测 + 判定”，RPO 由同步或异步复制决定。想同时要 RPO = 0 和低写入延迟，这两者不可兼得。

RTO、RPO 与脑裂：主备的三个约束

RTO 与 RPO：两个独立指标

RTO 表示恢复服务所需的时间，主要取决于“检测 + 判定”，主备通常为几十秒到几分钟。RPO 表示可能丢失的数据量，取决于复制方式。

同步复制RPO = 0拖慢主库写入
异步复制可能丢最后一段写入性能更好

两者不可兼得，需要根据业务对性能与一致性的要求做出取舍。

脑裂：主备最大的风险

网络分区时，主备都以为自己该服务，两边各写各的。必须有 fencing 机制：STONITH、仲裁节点、租约，把“谁是主”变成必须多数同意才能变更的事实。

主备的优势在于单写入者，数据一致性天然简单；写入路径唯一，不需要考虑冲突合并。

重点没有 fencing 的主备，在网络分区时会出现双主：两边都接受写入，数据可能被同时修改。仲裁、租约或 STONITH 必须保证“同一时刻只有一个主”。

仲裁、租约与 fencing：谁来判定“只有一个主”

故障检测只能说明“我联系不上对方”，不能证明“对方已经停止工作”。网络分区、GC 停顿、机器假死都会造成类似现象。如果备机仅凭“ping 不通”就提升自己，旧主可能仍在处理请求，于是出现双主。解决这个问题需要额外的仲裁机制，而不是更灵敏的心跳。

常见机制有三类。第一是多数派仲裁：只有获得超过半数投票者的同意，才能成为主；少数派一侧即使还有机器，也不能提供服务。第二是租约：主节点持有带过期时间的租约，必须在到期前续约，过期后自动失去写资格。第三是 STONITH（Shoot The Other Node In The Head）：在提升新主前，先通过电源、网络或存储隔离把旧主强制关掉。

还有一个容易被忽略的细节：客户端也要参与 fencing。旧主可能已经在本地完成写入，但它的写请求不应再被存储层接受。单调递增的 fencing token 可以让存储层拒绝旧主的请求：每次选主发放一个更大的 token，存储层只接受不小于已见最大值的写请求。

仲裁不是免费的：投票节点增加了部署复杂度，跨机房仲裁还会引入额外延迟；STONITH 则要求电源和网络可控。对于单机主备，至少应该使用 VIP 漂移加租约，避免“两台机器都认为自己持有 VIP”。

重点故障检测回答“我看不到谁”，仲裁回答“谁有资格写”。没有后者的自动切换，只是把故障从“服务不可用”升级成“数据双写”。

多活的实现方式

从只读多活到任意多写

多活的本质是并发写问题；所需的一致性强度，直接决定工程成本。

01

只读多活

简单

读流量分散到多地，写入仍回到主库。写侧仍是单点，同时受跨地域延迟约束。

一致性 强复杂度 低
02

分区多活 · 单元化

工程主流

按用户或租户把数据切片，每个单元只服务自己那片。单元内闭环，跨单元异步复制。

一致性 强复杂度 中
03

任意多写 + 冲突解决

一致性降级

LWW、CRDT、业务层合并。多个节点随时可写，代价是很多业务接受不了一致性降级。

一致性 可降级复杂度 高

三类方案的核心差异在于写入冲突由谁承担：只读多活把写留在主库，单元化把冲突限制在单元内部，任意多写则必须引入冲突解决机制。方案越靠后，并发能力越强，但一致性保障越弱、工程复杂度越高。选择时先看业务能否接受跨单元延迟和冲突合并，再决定投入哪一档。

重点工程上的异地多活，通常是“单元化 + 异步复制”，而不是任意节点都能写任意数据。任意多写必须引入 LWW、CRDT 或业务合并，一致性会降级。

跨地域强一致，基本不现实

Raft / Paxos 的多数派确认需要跨地域完成一次 RTT。北京到上海约 30ms，每次写入都需付出该延迟，吞吐会下降一个量级。因此工程上的“异地多活”，几乎都是单元化 + 异步复制，而不是“任意节点都能写任意数据”。

冲突解决：LWW、CRDT 与业务合并

一旦允许多个节点同时写同一条数据，冲突就不再是异常，而是常态。冲突解决不是“选一个看起来最新的值”这么简单，它决定了并发写入时哪一方会被保留、哪一方会被丢弃，以及业务能否接受这种丢弃。

三种常见冲突解决策略
策略做法代价适用数据
LWW · 最后写入获胜用时间戳或版本号决定保留哪次写入依赖时钟；并发写会静默丢失一方用户资料、偏好设置等可覆盖数据
CRDT · 无冲突复制数据类型使用可交换、可合并的数据结构，如计数器、集合、寄存器数据类型受限；元数据开销较大购物车、点赞数、在线状态
业务层合并把冲突暴露给业务规则，按领域语义合并实现复杂；需要业务方深度参与库存、订单、账务等强语义数据

更常见的做法不是“解决冲突”，而是“避免冲突”：按用户 ID、租户 ID 或订单 ID 做单元化路由，让同一条数据始终由同一个单元写入；对无法切分的数据保留单写入点；对跨单元操作使用幂等键和补偿事务，而不是并发写同一条记录。

无论采用哪种策略，都要回答三个问题：冲突发生的概率有多大？冲突时丢失一笔写，业务是否能接受？如果无法接受，是否应该改成串行写入？这三个问题比选择具体算法更重要。

重点冲突解决的核心不是技术选型，而是业务对“丢失或合并一次写”的容忍度。不能容忍，就不要让两个节点同时写同一条数据。

故障转移的工程细节：客户端也要配合

服务端完成切换，不代表用户请求就能恢复。客户端可能仍持有旧连接、仍在重试失败节点，或者因为超时时间过长而拖垮线程池。故障转移是一套端到端的协作机制，服务端、客户端和网络入口都要参与。

重试要有预算，不能无限放大

故障时大量客户端同时重试，会把已经紧张的节点再次压垮，形成重试风暴。正确做法是：只重试幂等请求；使用指数退避加随机抖动；为每次请求设置重试预算；当错误率超过阈值时快速失败，而不是继续重试。

隔离：别让一个依赖拖垮全部

舱壁模式（Bulkhead）把线程池、连接池或队列按依赖隔开。某个下游变慢时，只有对应的舱壁被占满，其他功能仍可用。配合超时、并发上限和队列上限，可以避免“一个慢接口拖垮整个进程”。

此外，客户端应缓存服务端地址并支持重新解析，避免 DNS 或 VIP 切换后仍连接旧地址；长连接需要设置合理的空闲超时；切换期间可以短暂返回降级结果，而不是让请求无限等待。故障转移的目标是“整体恢复”，不是“每个请求都成功”。

重点故障转移不是服务端的独角戏。没有超时、重试预算、熔断和舱壁，客户端会把一次局部故障放大成全局雪崩。

演练与混沌工程：验证冗余真的有效

冗余最大的风险不是“没有备机”，而是“以为有备机”。备机可能没有追平数据、配置可能不一致、VIP 可能漂移失败、客户端可能不会重连。这些问题只有在真实切换时才会暴露，因此必须通过演练提前发现。

演练可以从桌面推演开始：把架构图、依赖关系、切换步骤和联系人摆在桌面上，逐项走一遍。之后再做受控实验：在低峰期、小流量范围内注入故障，观察系统是否按预期恢复。每次演练都要有明确假设、影响范围和中止条件。

常见故障演练项目

重点没有被验证过的冗余，只是架构图上的假设。演练要从小范围开始，明确中止条件，并把发现的问题转成可跟踪的改进项。

01

冗余要隔离故障域；冷、温、热的差别是备机准备到了哪一步。

02

主备是单写入者模型；RTO 卡在检测与判定，RPO 由复制方式决定。

03

脑裂必须用仲裁、租约或 STONITH 解决；切换前先确保旧主不能写。

04

多活的核心是并发写；优先单元化，无法切分的数据保留单写入点。
