高可用架构

高可用，是不间断提供服务的能力。它不依赖某个永不故障的组件，而依赖一整套冗余与转移机制——从主备、多活，到负载均衡、容灾和限流。

01

可用性

可用性指标：几个 9 与停机预算

高可用用“几个 9”来度量。99.9% 是一年约 8.8 小时停机，99.99% 约 53 分钟，99.999% 只剩约 5 分钟。每多一个 9，停机时间缩小十倍，成本通常涨得更多。

其计算公式为：可用性 = 正常服务时间 ÷ 总时间。通常按年折算成停机分钟数。4 个 9 意味着全年停机小于 53 分钟；5 个 9 小于 5 分钟。这两个数字构成一年内可接受的停机预算。

如何读这张图：横条采用对数刻度，因为不同可用性水平之间的停机时间相差一个数量级。每增加一个 9，年度停机时间缩小为原来的十分之一，但达到下一级所需的工程投入通常远高于十倍：需要覆盖数据库、缓存、消息队列、网络和发布流程的整条链路。

串联链路的可用性：一个请求往往依次经过客户端、负载均衡、网关、应用和数据库。串联环节的可用性近似为各环节可用性的乘积，环节越多，整体可用性越低。因此提升整体可用性有两条路径：减少不必要的串行依赖，或为关键环节增加冗余与快速故障转移。

停机预算的用法：把年度允许停机时间视为预算，计划内发布、故障和演练都会消耗它。预算越紧，越需要自动化发布、灰度、回滚和故障演练；仅靠“机器不坏”无法达到高可用目标。

重点可用性按整条链路计算，而不是按单台机器计算。每增加一个 9，停机时间缩小十倍，工程成本通常远不止十倍。

02

冗余

主备与多活：单写入者与并发写

冗余是高可用的核心思想：通过额外的副本获得故障时的接管能力。主备与多活的根本差别，不在于机器数量，而在于同一时刻有多少个写入者。

主备 · active-passive

A 对外服务，B 是与 A 硬件、环境、部署完全一致的备用节点，持续复制数据但不对外服务。A 发生故障时，将写入权转移至 B。冷备、温备、热备的区别，在于备机的就绪程度。

多活 · active-active

A、B、C 同时对外服务并接受写入。单个节点故障不会中断服务，但多个节点同时修改同一条数据时，必须解决写入冲突。

从演练台可以看到，主备切换不是一次瞬时动作，而是“检测 → 判定 → 提升 → 切流”的连续过程。RTO 主要消耗在前两步：检测要等心跳超时，判定要避免网络抖动导致误切；真正提升备机和切换 VIP 反而很快。因此缩短 RTO 的关键，是设计可靠的故障检测与仲裁机制，而不是单纯提高机器性能。

RPO 则由复制方式决定。同步复制要求主库等待备库确认，故障时数据不丢，但写入延迟上升；异步复制先返回客户端，性能更好，故障瞬间可能丢失尚未复制的那一段写入。选择哪一种，取决于业务能否接受数据缺失。

重点RTO 主要卡在“检测 + 判定”，RPO 由同步或异步复制决定。想同时要 RPO = 0 和低写入延迟，这两者不可兼得。

RTO 与 RPO：两个独立指标

RTO 表示恢复服务所需的时间，主要取决于“检测 + 判定”，主备通常为几十秒到几分钟。RPO 表示可能丢失的数据量，取决于复制方式。

同步复制RPO = 0拖慢主库写入
异步复制可能丢最后一段写入性能更好

两者不可兼得，需要根据业务对性能与一致性的要求做出取舍。

脑裂：主备最大的风险

网络分区时，主备都以为自己该服务，两边各写各的。必须有 fencing 机制：STONITH、仲裁节点、租约，把“谁是主”变成必须多数同意才能变更的事实。

主备的优势在于单写入者，数据一致性天然简单；写入路径唯一，不需要考虑冲突合并。

重点没有 fencing 的主备，在网络分区时会出现双主：两边都接受写入，数据可能被同时修改。仲裁、租约或 STONITH 必须保证“同一时刻只有一个主”。

多活的实现方式

从只读多活到任意多写

多活的本质是并发写问题；所需的一致性强度，直接决定工程成本。

01

只读多活

简单

读流量分散到多地，写入仍回到主库。写侧仍是单点，同时受跨地域延迟约束。

一致性 强复杂度 低
02

分区多活 · 单元化

工程主流

按用户或租户把数据切片，每个单元只服务自己那片。单元内闭环，跨单元异步复制。

一致性 强复杂度 中
03

任意多写 + 冲突解决

一致性降级

LWW、CRDT、业务层合并。多个节点随时可写，代价是很多业务接受不了一致性降级。

一致性 可降级复杂度 高

三类方案的核心差异在于写入冲突由谁承担：只读多活把写留在主库，单元化把冲突限制在单元内部，任意多写则必须引入冲突解决机制。方案越靠后，并发能力越强，但一致性保障越弱、工程复杂度越高。选择时先看业务能否接受跨单元延迟和冲突合并，再决定投入哪一档。

重点工程上的异地多活，通常是“单元化 + 异步复制”，而不是任意节点都能写任意数据。任意多写必须引入 LWW、CRDT 或业务合并，一致性会降级。

跨地域强一致，基本不现实

Raft / Paxos 的多数派确认需要跨地域完成一次 RTT。北京到上海约 30ms，每次写入都需付出该延迟，吞吐会下降一个量级。因此工程上的“异地多活”，几乎都是单元化 + 异步复制，而不是“任意节点都能写任意数据”。

03

负载均衡

负载均衡：高可用与水平扩展的入口

负载均衡同时承担高可用与水平扩展：单节点故障时由其他节点接管；负载上升时通过增加节点分担。作为所有流量的入口，负载均衡层自身也必须具备高可用能力。

HARDWARE

硬负载

F5、Radware 等专用设备。性能强、稳定性高，但成本高、扩展灵活性有限。

SOFTWARE

软负载

Nginx、LVS、HAProxy 等软件。成本低、部署灵活，是大多数系统的默认选择。

F5 Nginx HAProxy LVS

负载均衡位于客户端与后端服务之间，一方面把请求分摊到多个节点，另一方面通过健康检查把故障节点从转发列表中移除。它同时解决“单节点容量有限”和“单节点故障”两个问题，但自身也成为新的单点，因此需要双机主备或多级冗余。

按工作层次，负载均衡分为四层和七层：四层只看 IP 与端口，转发开销小；七层能解析 HTTP，按 URL、Header 路由，适合灰度、改写和细粒度限流。层次越高，能力越强，性能开销也越大。

下面的模拟器使用三个权重与处理速度不同的节点。切换策略可以观察请求分布如何变化；将某个节点下线，可以观察负载均衡器如何避开故障节点。

重点负载均衡同时解决“容量不足”和“单节点故障”，但它自身也是新的单点；入口层必须做双机主备或多级冗余。

    会话保持还有一个副作用：节点扩缩容时哈希映射会变化，部分用户会被重新分配到其他节点，原有会话可能失效。因此现代系统更倾向于把会话状态外置到 Redis 等共享存储，而不是依赖 IP 哈希。

    负载均衡层自身的高可用

    双机主备与多级冗余

    负载均衡器自身是流量入口，一旦不可用，后端再健康也无法访问。常见的做法是双机主备：两台 Nginx 通过 Keepalived 绑定同一个 VIP，由 VRRP 决定谁持有 VIP；主节点故障时，备节点在数秒内接管 VIP。需要注意，VIP 漂移只解决入口故障，不能提升单机 Nginx 的连接数上限，因此高并发场景还需要多级负载。

    多级负载把不同层次的设备串联起来：硬负载负责最外层的高吞吐，LVS/HAProxy 做四层转发，Nginx 做七层路由与应用层能力。每一层都可以用 Keepalived 做成主备，从而避免任何单台设备成为整条链路的单点。

    Nginx + Keepalived 双机主备

    • 两台 Nginx 各自独立 IP，都装 Keepalived，并绑定同一个虚拟 IP。
    • 主节点存活时流量走主；主宕机后 VIP 自动漂移到备节点，完成故障转移。
    • 原主恢复后自动变成备机。两台 Nginx 的配置必须时刻完全一致。
    • 缺点：同一时间只有一台对外服务，单机连接数有限，Nginx 本身无法水平扩展。

    应用服务业务处理

    LVS / HAProxy 专注四层转发，性能比 Nginx 强很多；多级结构让 Nginx 也能水平扩展，支撑超高并发。

    四层负载

    传输层 · TCP / UDP

    只看 IP 和端口，转发快、开销小。代表：LVS、HAProxy、F5。

    七层负载

    应用层 · HTTP / HTTPS

    能读 URL、Header，做路由、改写、限流。代表：Nginx。新版 Nginx 也可用 stream 模块做四层。

    重点四层只读取 IP 与端口，转发快；七层能解析 HTTP，能力灵活但开销更大。多级负载把两者叠加，才能同时获得高吞吐与水平扩展。

    负载策略

    常见负载策略及其适用假设

    轮询

    按顺序轮流分配，简单均匀。

    权重轮询

    能力强的节点多接，按权重比例分配。

    动态权重轮询

    根据 CPU、内存、IO 算权重，让空闲的节点多接。

    最小连接数

    每次给当前连接数最少的机器。

    最短响应

    发给响应时间最快的服务器。

    IP 哈希

    同一来源固定落到同一节点，用来保 session。

    URL 哈希

    同一类 URL 固定落到同一节点，便于缓存。

    最小会话

    优先选择当前会话数最少的节点。

    趋势分析

    按请求变化趋势提前调度，适合可预测的流量。

    随机

    随机挑一台；量大时趋近均匀，短窗口会抖动。

    选择策略时先回答三个问题：服务是否有状态、节点能力是否一致、流量是否可预测。无状态且节点同构，轮询或随机即可；节点异构，用加权或最少连接；需要会话保持，用 IP 哈希；流量有明显趋势，可用趋势分析。会话保持会带来一个副作用：节点扩缩容时映射变化，部分会话会失效，因此更稳妥的做法是把会话状态外置到共享存储。

    DNS 轮询

    DNS 轮询：最外层的负载分担

    域名绑定多个 IP，DNS 按顺序依次返回，用户请求被分配到不同地址，服务因此可以水平扩展。

    但它有两个明显限制：服务器直接暴露在互联网上；吞吐依然不足。更常见的是 DNS + 多级负载——域名解析到 LVS 的 VIP，再由 LVS 和 Nginx 分发，后端不暴露。

    没有健康检查

    DNS 没有主动探测机制。某个节点宕机，DNS 不会自动把它的 IP 从列表里摘掉，用户仍会被解析到坏节点。DNS 轮询做不到自动故障转移。

    图示：DNS 按顺序返回三个 IP，其中 IP 3 已宕机但仍会被返回。

    重点DNS 轮询没有健康检查，节点宕机后坏 IP 不会被自动摘除，因此 DNS 轮询不能独立完成故障转移。

    容灾

    容灾架构：同城热备与异地多活

    容灾将机房级故障纳入可用性范围。两地三中心侧重快速接管，异地多活让多个数据中心同时提供服务；两者都以成本换取恢复能力。

    同一时间只有 DC 1 对外服务；DC 2 保持环境一致，DC 3 只做数据备份。

    灾备切换并不只是修改一条 DNS 记录：数据库需要确认复制位点，备用中心需要具备完整的运行环境和最新配置，客户端与 DNS 缓存还要等待 TTL 过期。因此真实的灾备切换依赖详细的运行手册和定期演练，而不是临时操作。日常发布必须在两个中心都执行，正是为了避免“主中心能跑、备中心跑不起来”。

    跨地域复制通常依赖专线，带宽和延迟都会影响 RPO。灾备方案设计时，需要把数据同步方式、切换判定条件、回切流程和演练频率一起确定，否则备用中心只是名义上存在。

    重点两地三中心是“单活 + 热备”：同一时间只有一个数据中心对外服务。切换依赖数据同步、环境一致性和反复演练；备用中心长期不运行，切换时未必可靠。

    两地三中心的运行方式

    • 同城或邻近城市（如深圳、东莞）建两个数据中心，距离近、延迟低，数据几乎实时同步。
    • 一个数据中心发生火灾、地震等毁灭性事故，快速切到另一个，短时间恢复服务。
    • 两个都不可用时，在更远的位置（如上海）用备份数据重建。
    • 日常发布——代码、数据库 DDL、环境配置——必须在两个 DC 都执行，保证环境完全一致。
    • 数据库主从同步；跨地域同步有延迟，需要拉专线。

    热备的代价

    始终有一个数据中心处于闲置状态，资源利用率低，成本浪费明显。更重要的是，备用数据中心长期没有真实业务，实际切换时未必能可靠运行。

    节省成本的做法：只给核心业务做灾备，灾难时优先保证核心系统。

    异地多活

    多个数据中心同时提供服务

    全国乃至全球部署，让用户访问最近的数据中心。部署成本极高，技术复杂，资金和人员投入巨大。

    深圳读写 · 单元 C

    多活数据中心同时服务；跨地域复制是异步的，延迟无法避免。

    异地多活的核心不是多建几个机房，而是把流量和数据按单元切开。每个单元只服务一部分用户，交易在单元内闭环，跨单元只做异步复制。这样既能就近接入降低延迟，也能在单个单元故障时把流量切到其他单元。代价是单元之间存在复制延迟，跨单元查询可能读到旧值。

    单元划分需要稳定的分片维度，例如用户 ID 或租户 ID；划分之后，用户归属、数据迁移和扩容都会成为长期约束。这也是异地多活“技术复杂、投入巨大”的主要原因。

    重点异地多活是多活：多个数据中心同时服务，单点故障时流量自动绕开。代价是接受异步复制延迟，并把业务按稳定维度切成单元。

    难点一：跨 DC 调用慢

    分布式系统里，一个请求可能发生数十次服务调用。如果这些调用不能发生在同一个 IDC 内，延迟就会叠高。

    所以异地多活的第一个要求：尽量让一笔交易在同一个 IDC 内闭环，避免跨区访问。

    难点二：数据无法实时同步

    距离带来延迟，复制无法做到实时。用户在北京下单，订单查询却到了上海，就可能看到旧数据。

    伪异地多活：数据库不拆分也不同步，集中在一个 IDC，多地服务共享一套数据源，以一致性换取实现简单。真异地多活：各 DC 数据库独立部署，再通过同步复制，延迟无法避免。

    不是所有业务都适合异地多活

    账户余额、转账等对一致性与实时性要求极高的业务不适合异地多活；低频交易通常也无需采用该架构。登录频率高且是业务入口，适合多活；用户资料修改频率低，通常无需为此投入多活成本。异地双活是异地多活的特例：两个远距离城市同时提供服务。

    两地三中心 vs 异地多活
    两地三中心异地多活
    服务形态单活 + 热备，同一时间一个 DC 服务多活，多个 DC 同时服务
    故障切换分钟级，需要切换流程接近 0，流量绕开
    访问延迟集中在同城，远处用户慢就近接入，全国/全球更快
    成本中，备用 DC 闲置极高，技术复杂
    典型用途灾备合规、核心系统兜底全国/全球业务、单元化架构
    05

    中间件

    中间件高可用：冗余与故障转移的不同实现

    MongoDB、Redis、Kafka、MySQL 的高可用，底层都是冗余加故障转移，但副本粒度、选举方式和一致性取舍各不相同。理解其共性，比记忆各产品的配置项更重要。

    MongoDB：副本集与分片

    副本集解决单节点故障，分片解决单机容量。两者可以叠加：每个分片本身就是一个副本集。

    副本集解决的是节点级故障：多数节点存活，即可选举出新的主节点。分片解决的是单机容量：数据按分片键分布到多个 shard，每个 shard 本身又是一个副本集。两者叠加，才能同时获得故障转移和水平扩展能力。

    下面先看整体结构，再看主从、副本集与分片三种部署形态。

    CLIENT应用
    →
    ROUTERmongos请求转发到分片

    CONFIG SERVERS · CSRS

    存储分片元信息，本身用高可用方式部署；mongos 靠它知道数据在哪。

    主从

    已废弃 · 不推荐

    用法一：从库只做实时备份，不干活。用法二：读写分离，从库只读。没有故障转移，宕机必须手动切库，应用还得改连接信息。

    副本集

    推荐

    选举出 master 负责读写，其他副本承担备份和读操作；节点间心跳判定可用；每个节点都保存全量数据。

    分片

    水平扩展

    三个角色：shard、router、config servers。只对部分集合分片；未分片的集合必须放在主分片；分片键选中后不能改。

    分片算法

    选键之后不可改
    HASH

    均匀，但不连续。

    RANGE

    连续区间，可能不均匀，末尾分片容易成热点。

    重点副本集解决节点故障，分片解决单机容量；分片键一旦选定不可修改。Hash 分片均匀但范围查询要扫多个分片，Range 分片利于范围查询但容易出现热点。

    Redis：内存存储、持久化与缓存失效

    数据全在内存里，读写性能远超关系型数据库，通常作为缓存减少数据库访问和磁盘读写。高可用之外，先要照顾持久化和缓存失效。

    Redis 的高可用可以拆成两个问题：数据不能全丢（持久化），服务不能停（主从、哨兵、集群）。两者目标不同，配置也经常需要权衡。

    持久化：RDB 与 AOF

    RDB

    周期性快照。主进程 fork 子进程备份，对性能影响较低，恢复和重启更快。缺点是丢数据：5 分钟备份一次，宕机最多丢 5 分钟。

    AOF

    每条命令记日志。回放恢复，文件会变大，需要重写合并重复命令；恢复速度不如 RDB。

    always

    每次写完立即 fsync。最稳，一般不用。

    no

    交给操作系统调度。性能最好，丢失风险最高且不可控。

    everysec推荐

    每秒 fsync，最多丢最近 1 秒。

    缓存失效的三种典型场景

    雪崩

    大规模缓存同时失效，大量请求直接打数据库。

    延伸：过期时间打散、多级缓存

    击穿

    某个热点缓存失效，大量请求全打数据库。

    延伸：互斥锁、逻辑过期

    穿透

    请求查缓存里根本没有的数据，直接越过缓存打数据库。

    延伸：布隆过滤器、缓存空值

    Redis 的三种高可用架构

    主从

    基础

    一主一从、一主多从、主从从。主库读写，从库备份或分担读。同步分三种：全量同步（SYNC → fork 生成 RDB → 缓存期间的写 → 发送 → 从库加载）、增量同步（把缓存的写指令发给从库）、部分同步（断联后 PSYNC 从上次位置续传）。不能自动故障切换，必须手动把从改为主。

    哨兵

    自动转移

    在主从基础上增加哨兵节点，组成“仲裁委员会”。哨兵不存业务数据；每 10 秒向主节点发 info 获取拓扑，每秒 ping 主、从和其他哨兵。单个哨兵判断是主观下线；超过半数哨兵认为不可用，才是客观下线。随后选举领头哨兵，把一个从节点（ID 较小）升级为主，其他从节点指向新主，并通知客户端。原主恢复后自动变从。本质是高可用读写分离：只有主节点对外读写。

    集群

    海量数据

    分布式系统，每个节点存部分数据；多主多从，主故障时从节点被选举为主。固定 16384 个哈希槽，每个节点管理一部分。适合海量数据、高并发、高可用；数据量不大没必要上集群。

    断联重连时用 PSYNC 从上次偏移量继续（部分同步），不必每次都全量复制。

    Kafka：分区副本撑起高可用

    消息先进入分区，分区有 Leader 和 Follower 副本；Leader 故障，Follower 被选举上位。高可用发生在“分区”这一级，而不是整台 Broker。

    Kafka 的高可用单位是分区，而不是 Broker。每个分区有一个 Leader 和若干 Follower；生产者只写 Leader，Follower 持续拉取复制。Leader 故障后，集群从同步副本中选举新的 Leader，分区继续可写。

    POINT-TO-POINT

    点对点

    生产者把消息发到队列，多个消费者监听，但一条消息只有一个消费者能消费。

    PUB / SUB

    订阅

    生产者把消息发到主题，订阅了这个主题的消费者都能收到。

    高吞吐 · 低延迟可用 · 可扩展持久 · 可靠容错高并发

    • 集群借助 ZooKeeper 存节点元数据，实现 Broker 高可用；新版 Kafka 也支持不依赖 ZooKeeper 的 KRaft 模式。
    • 每个主题划分多个分区，消息按算法分配到不同分区；分区不可用会丢数据，所以用分区副本兜底。
    • 生产者写 Leader 副本，Leader 同步给 Follower；Leader 故障，选举一个 Follower 升为 Leader。

    重点Kafka 的高可用单位是分区：Leader 故障后由同步副本接替，分区继续可写。Broker 数量并不等于副本数量，扩分区时还要考虑副本分布。

    MySQL：主从复制与一致性取舍

    主备、主从、互为主从解决读扩展和备份，真正的取舍在复制策略：等不等从库，等几个从库。

    MySQL 的高可用主要围绕复制展开：主库把变更写入 binlog，从库拉取并回放。主备、主从、互为主从的区别，是复制拓扑和读写入口不同；异步、半同步、全同步的区别，是主库何时向客户端确认。

    主备

    备份

    一个主库一个备库，主库实时同步到备库。备库不提供任何服务，长期闲置；主库故障不能自动转移，必须由 DBA 手动切换。

    主从

    读扩展

    一主一从、一主多从、主从从。从库分担读压力，但主库的写压力并没有减轻。

    互为主从

    写扩展 · 复杂度高

    两个节点都支持读写，数据相互同步，读写能力同时提高。难点是主键不能冲突，一旦数据不一致将很难恢复。

    策略客户端何时收到响应一致性风险 / 代价
    异步复制MySQL 默认
    主库提交事务后立即返回
    0 个从库确认
    响应最快；主库宕机时，未同步的数据会丢
    全同步复制强一致
    所有从库都执行完事务才返回
    全部从库确认
    严格一致；等待最久，从库越多越慢
    半同步复制平衡
    至少一个从库确认接收就返回
    ≥ 1 个从库确认
    响应与一致性的中间态，不需要等所有从库

    异步复制下，如果主库在数据到达从库前宕机，切到从库就会缺一段数据；这是拿一致性换响应速度的典型交易。

    重点异步复制快，但主库故障时可能丢数据；全同步一致性强，但等待所有从库、延迟最高；半同步只等至少一个从库确认，是两者的折中。复制策略不等于自动故障转移。

    限流

    限流：以系统可用性为目标

    大促期间流量激增，限流的目标不是让每个请求都成功，而是避免系统整体宕机，保障大多数核心功能可用。类似游戏在负载过高时降低画质以保证流畅度，限流通过降低部分请求的体验来维持整体可用性。

    限流要发生在客户端、负载设备、网关、应用系统等多个节点；算法核心是漏桶和令牌桶。最终目的只有一个：减轻后端服务与数据库的压力。

    客户端层验证码 · 禁用按钮 · 调用限制 · 假排队
    负载层Nginx / LVS / HAProxy 限速与连接数
    服务层网关按服务、接口、用户、IP 限流
    数据层最后一道防线，绝不能被打垮

    倒金字塔限流

    越往上，越适合挡流量

    越靠近上层，事务处理压力越小，应对高并发的能力越强；越靠近底层，处理事务的能力越强，反而越怕被压垮。

    因此流量应自上而下逐层递减：客户端先行拦截，负载层削峰，服务层按业务规则限制，数据层仅承接剩余流量。

    客户端限流

    成本最低的一层

    大多数用户不会主动发起服务攻击。客户端限流主要针对高频操作与误触，投入低、见效快。

    纯前端验证码

    请求过于频繁时弹出图片验证码，打断操作，区分人为还是机器。可由 JavaScript 前端生成，不需要考虑安全性。

    禁用按钮

    点击后立即禁用，直到收到服务端应答，防止用户因急躁反复点击造成重复请求。

    调用限制

    限制用户 1 秒内可发起的请求次数，超出时提示“您的操作过于频繁，请少安毋躁”。

    假排队

    提示“当前繁忙，正在排队 1/10 人”或“预计等待 5 秒”，人数和秒数随机，把请求摊开，减少同一时刻的并发。

    重点客户端限流成本最低，但只能挡住一部分请求；服务端必须在负载层、网关、服务层和数据层逐层限流，形成倒金字塔。

    漏桶 / 令牌桶模拟器 RATE LIMIT
    通过0
    排队中0
    拒绝0
    队列 0 / 10
    下游服务固定速率流出

    漏桶算法：请求进入队列排队，桶满后拒绝；下游按固定速率取走请求。突发流量会被削平，代价是排队等待。

    服务端限流：Nginx 两个模块

    ngx_http_limit_req_module 控制请求速率，ngx_http_limit_conn_module 控制连接数。负载设备是流量入口，最适合在这里先削一层。

    limit_req_zone $binary_remote_addr zone=req:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;

server {
    limit_req zone=req burst=20 nodelay;
    limit_conn conn 20;
}

    网关限流：按业务维度细分

    用户、订单、库存微服务面临的压力不同，可以只针对订单服务限流，甚至只针对某个接口、某个用户、某个 IP、某个时间段限流。

    灵活度高，是微服务架构里最常用的一层精细限流。配合客户端的粗粒度拦截和 Nginx 的入口限速，形成完整的倒金字塔。

    分层顺序

    客户端拦截 → 入口削峰 → 网关按业务限流 → 数据层承接剩余流量。

    重点漏桶把突发削成平滑输出，代价是排队或拒绝；令牌桶允许突发通过，适合有明显峰谷的互联网流量。实际系统常把两者组合：入口用令牌桶吸收突发，下游用漏桶保护数据库。
