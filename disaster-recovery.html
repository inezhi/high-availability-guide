第 04 章 · 机房

容灾：从同城热备到异地多活

暴雨导致同城机房断电。团队切到备用中心，才发现证书过期、依赖缺失，备用中心根本跑不起来。本章从这次失败的切换出发，先定义容灾等级，再讨论两地三中心、异地多活和演练。

容灾的范围：先定义故障域

先问一个更基本的问题：这次暴雨，备用机房到底能防住哪一种故障？

做容灾设计，第一步不是选机房，而是定义要防什么：单机故障、机架掉电、机房断电、城市灾害，还是区域级网络中断？不同故障域对应不同的隔离距离和成本。防单机故障用多副本即可；防城市灾害必须把副本放到足够远的位置，而这又会带来复制延迟。

第二步是定义恢复目标：RTO 决定“多久恢复”，RPO 决定“能丢多少数据”。目标不同，方案可能相差一个数量级。一个能接受小时级恢复、分钟级数据丢失的业务，用备份加冷备就够了；一个要求秒级恢复、零数据丢失的核心交易，才需要双活和多副本同步。

重点容灾先定义故障域与 RTO / RPO，再选方案。防城市灾害的副本必须放得足够远，而距离会直接转化为复制延迟和成本。

定义了故障域和恢复目标，接下来要把容灾分成可选择的几档。比较容灾等级

容灾的四个等级：从备份到双活

“做了容灾”可以指很多种不同的东西。按恢复方式和成本，通常分为四档：备份与恢复、冷备、温备、双活或多活。它们不是互斥的，核心系统可能用双活，周边系统只用备份恢复。

容灾等级与适用场景
等级备用环境典型 RTO典型 RPO适合业务
备份 / 恢复只有离线备份，需要时重建小时到天上次备份点内部工具、归档数据、非核心系统
冷备机器和网络就绪，应用和数据需恢复小时级备份频率决定可接受较长停机的业务
温备环境运行，数据持续复制，不接流量分钟级复制延迟大多数核心业务的灾备
双活 / 多活多个中心同时服务，流量可切换秒级或接近 0异步复制窗口支付、登录、全国性业务

等级越高，日常成本越高，但“RTO 更短”并不意味着“更可靠”。双活需要解决数据冲突、流量调度和容量冗余；温备如果长期不演练，切换时同样可能失败。选择时应把“恢复目标”和“验证能力”一起考虑，而不是只买更贵的设备。

重点容灾等级不是越高越好，而是要与业务损失匹配。核心系统可以双活，非核心系统用备份恢复更经济；每一档都必须有演练和回切预案。

对多数企业，温备加两地三中心是成本与恢复速度的折中。看两地三中心怎么运行

两地三中心：单活 + 热备

对这家公司来说，完全双活太贵，只做备份又太慢。他们最终选择了同城双中心加异地备份——也就是常说的两地三中心。

同一时间只有 DC 1 对外服务；DC 2 保持环境一致，DC 3 只做数据备份。

灾备切换并不只是修改一条 DNS 记录：数据库需要确认复制位点，备用中心需要具备完整的运行环境和最新配置，客户端与 DNS 缓存还要等待 TTL 过期。因此真实的灾备切换依赖详细的运行手册和定期演练，而不是临时操作。日常发布必须在两个中心都执行，正是为了避免“主中心能跑、备中心跑不起来”。

跨地域复制通常依赖专线，带宽和延迟都会影响 RPO。灾备方案设计时，需要把数据同步方式、切换判定条件、回切流程和演练频率一起确定，否则备用中心只是名义上存在。

重点两地三中心是“单活 + 热备”：同一时间只有一个数据中心对外服务。切换依赖数据同步、环境一致性和反复演练；备用中心长期不运行，切换时未必可靠。

两地三中心的运行方式

  • 同城或邻近城市（如深圳、东莞）建两个数据中心，距离近、延迟低，数据几乎实时同步。
  • 一个数据中心发生火灾、地震等毁灭性事故，快速切到另一个，短时间恢复服务。
  • 两个都不可用时，在更远的位置（如上海）用备份数据重建。
  • 日常发布——代码、数据库 DDL、环境配置——必须在两个 DC 都执行，保证环境完全一致。
  • 数据库主从同步；跨地域同步有延迟，需要拉专线。

热备的代价

始终有一个数据中心处于闲置状态，资源利用率低，成本浪费明显。更重要的是，备用数据中心长期没有真实业务，实际切换时未必能可靠运行。

节省成本的做法：只给核心业务做灾备，灾难时优先保证核心系统。

但业务走向全国后，单活热备的延迟和闲置成本开始显现。走向异地多活

异地多活：多个数据中心同时服务

全国乃至全球部署，让用户访问最近的数据中心。部署成本极高，技术复杂，资金和人员投入巨大。

北京读写 · 单元 A
上海读写 · 单元 B
深圳读写 · 单元 C

多活数据中心同时服务；跨地域复制是异步的，延迟无法避免。

异地多活的核心不是多建几个机房，而是把流量和数据按单元切开。每个单元只服务一部分用户，交易在单元内闭环，跨单元只做异步复制。这样既能就近接入降低延迟，也能在单个单元故障时把流量切到其他单元。代价是单元之间存在复制延迟，跨单元查询可能读到旧值。

单元划分需要稳定的分片维度，例如用户 ID 或租户 ID；划分之后，用户归属、数据迁移和扩容都会成为长期约束。这也是异地多活“技术复杂、投入巨大”的主要原因。

重点异地多活是多活：多个数据中心同时服务，单点故障时流量自动绕开。代价是接受异步复制延迟，并把业务按稳定维度切成单元。

难点一：跨 DC 调用慢

分布式系统里，一个请求可能发生数十次服务调用。如果这些调用不能发生在同一个 IDC 内，延迟就会叠高。

所以异地多活的第一个要求：尽量让一笔交易在同一个 IDC 内闭环，避免跨区访问。

难点二：数据无法实时同步

距离带来延迟，复制无法做到实时。用户在北京下单，订单查询却到了上海，就可能看到旧数据。

伪异地多活：数据库不拆分也不同步，集中在一个 IDC，多地服务共享一套数据源，以一致性换取实现简单。真异地多活：各 DC 数据库独立部署，再通过同步复制，延迟无法避免。

不是所有业务都适合异地多活

账户余额、转账等对一致性与实时性要求极高的业务不适合异地多活；低频交易通常也无需采用该架构。登录频率高且是业务入口，适合多活；用户资料修改频率低，通常无需为此投入多活成本。异地双活是异地多活的特例：两个远距离城市同时提供服务。

两地三中心 vs 异地多活
两地三中心异地多活
服务形态单活 + 热备，同一时间一个 DC 服务多活，多个 DC 同时服务
故障切换分钟级，需要切换流程接近 0，流量绕开
访问延迟集中在同城，远处用户慢就近接入，全国/全球更快
成本中，备用 DC 闲置极高，技术复杂
典型用途灾备合规、核心系统兜底全国/全球业务、单元化架构

多活不是目的，故障时还要能切、能验证、能回切。把切换写成脚本

切换与回切：一场有脚本的协同

灾备切换不是“把 DNS 指过去”这么简单。它至少包括：确认灾难范围和影响、冻结写入或停止旧中心、确认数据复制位点、提升备用中心、验证核心链路、切换流量入口、观察错误率和延迟，最后才逐步放开全部流量。每一步都需要明确的负责人和中止条件。

回切同样重要。灾难恢复后，旧中心的数据可能落后于新中心，直接切回会丢失这段时间的写入。正确做法是先把旧中心作为从库追平数据，再在低峰期做一次受控回切；回切前要确认新中心的增量已经同步，回切后要保留一段双写或只读校验窗口。

DNS 切换还要考虑缓存 TTL。即使 GSLB 已经把坏机房摘除，部分用户仍可能按旧 TTL 访问旧地址。因此关键业务的 TTL 通常设置得较短，并配合客户端重试、备用域名或 Anycast 入口，避免把全部恢复时间押在一次 DNS 解析上。

组织层面要提前明确“谁有权宣布灾难”。如果没有授权，技术人员会在故障初期反复确认，错过最佳切换窗口；如果授权过于随意，又可能因为一次网络抖动误切，造成更大范围的中断。通常需要“技术负责人 + 业务负责人”共同确认，并把判定条件写进运行手册。

重点灾备切换是一次有脚本的协同，不是一条命令。切换前要能冻结旧中心，切换后要能验证数据；回切要先追平，再受控切回。

切换能否成立，最终取决于数据复制到了哪里。看复制方式与丢失窗口

数据复制：容灾的地基

容灾方案的上限由数据复制决定。同城两中心距离近，可以使用同步复制获得 RPO = 0；跨地域距离远，同步复制会让每次写入都等待一次广域网往返，吞吐显著下降，因此通常采用异步复制，并接受一个有限的丢失窗口。

复制方式之外，还要关注复制链路本身的高可用：专线可能中断，复制可能延迟，主库可能因为大事务产生复制堆积。监控复制延迟、校验数据一致性、定期做恢复演练，比单纯配置“异步复制”更重要。

不同距离下的复制取舍
场景常见复制方式RPO主要代价
同机房多副本同步 / 半同步0 或接近 0写入延迟略增
同城双中心同步 / 半同步0 或接近 0专线成本、仲裁复杂度
异地灾备异步复制秒到分钟灾难时可能丢失最后一段写入
跨国多活异步 + 单元化秒级窗口冲突解决、路由与数据归属

重点RPO 不是配置出来的，而是复制链路、距离和业务写入模式共同决定的。跨地域强同步会牺牲吞吐，异步复制则必须接受一个丢失窗口。

复制配置好了，也不代表备用中心真的能跑。用演练验证一切

演练与组织：备用中心必须“真的能跑”

容灾最常见的失败不是技术方案不对，而是备用中心长期不运行：配置漂移、证书过期、依赖缺失、容量不足、联系人变更。真正切换时，问题会集中爆发。解决方式只有一个：定期演练，并把演练发现的问题纳入日常发布流程。

演练可以从桌面推演开始，再做单组件切换，最后做全链路切换。每一次都要记录实际 RTO、数据丢失量、失败步骤和人工决策耗时。演练不一定非要停掉生产；可以通过流量镜像、灰度切换、只读验证等方式降低影响。

重点备用中心必须真的能跑。容灾能力不是购买来的，而是通过反复演练、修复和自动化逐步建立的。
