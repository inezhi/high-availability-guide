大促期间流量激增，限流的目标不是让每个请求都成功，而是避免系统整体宕机，保障大多数核心功能可用。类似游戏在负载过高时降低画质以保证流畅度，限流通过降低部分请求的体验来维持整体可用性。

限流要发生在客户端、负载设备、网关、应用系统等多个节点；算法核心是漏桶和令牌桶。最终目的只有一个：减轻后端服务与数据库的压力。

客户端层验证码 · 禁用按钮 · 调用限制 · 假排队
负载层Nginx / LVS / HAProxy 限速与连接数
服务层网关按服务、接口、用户、IP 限流
数据层最后一道防线，绝不能被打垮

倒金字塔限流

越往上，越适合挡流量

越靠近上层，事务处理压力越小，应对高并发的能力越强；越靠近底层，处理事务的能力越强，反而越怕被压垮。

因此流量应自上而下逐层递减：客户端先行拦截，负载层削峰，服务层按业务规则限制，数据层仅承接剩余流量。

客户端限流

成本最低的一层

大多数用户不会主动发起服务攻击。客户端限流主要针对高频操作与误触，投入低、见效快。

纯前端验证码

请求过于频繁时弹出图片验证码，打断操作，区分人为还是机器。可由 JavaScript 前端生成，不需要考虑安全性。

禁用按钮

点击后立即禁用，直到收到服务端应答，防止用户因急躁反复点击造成重复请求。

调用限制

限制用户 1 秒内可发起的请求次数，超出时提示“您的操作过于频繁，请少安毋躁”。

假排队

提示“当前繁忙，正在排队 1/10 人”或“预计等待 5 秒”，人数和秒数随机，把请求摊开，减少同一时刻的并发。

重点客户端限流成本最低，但只能挡住一部分请求；服务端必须在负载层、网关、服务层和数据层逐层限流，形成倒金字塔。

漏桶算法：请求进入队列排队，桶满后拒绝；下游按固定速率取走请求。突发流量会被削平，代价是排队等待。

服务端限流：Nginx 两个模块

ngx_http_limit_req_module 控制请求速率，ngx_http_limit_conn_module 控制连接数。负载设备是流量入口，最适合在这里先削一层。

limit_req_zone $binary_remote_addr zone=req:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;

server {
    limit_req zone=req burst=20 nodelay;
    limit_conn conn 20;
}

网关限流：按业务维度细分

用户、订单、库存微服务面临的压力不同，可以只针对订单服务限流，甚至只针对某个接口、某个用户、某个 IP、某个时间段限流。

灵活度高，是微服务架构里最常用的一层精细限流。配合客户端的粗粒度拦截和 Nginx 的入口限速，形成完整的倒金字塔。

分层顺序

客户端拦截 → 入口削峰 → 网关按业务限流 → 数据层承接剩余流量。

重点漏桶把突发削成平滑输出，代价是排队或拒绝；令牌桶允许突发通过，适合有明显峰谷的互联网流量。实际系统常把两者组合：入口用令牌桶吸收突发，下游用漏桶保护数据库。
