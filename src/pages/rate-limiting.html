第 06 章 · 保护

限流与过载保护：让系统在洪峰中活下来

双 11 零点，流量在 30 秒内涨了八倍。系统没有把所有人拒之门外，而是按层丢掉了一部分请求。听起来残酷，但总比大家一起卡死好。

系统是怎么被压垮的

先理解一个反直觉的事实：请求越多，吞吐不一定越高。

系统在低负载时，吞吐随请求量线性上升；接近容量上限后，排队开始变长，延迟上升；超过拐点后，线程、连接和内存被占满，重试又放大请求量，吞吐反而急剧下降。这就是过载崩溃：不是机器坏了，而是系统把全部资源花在了“处理已经无法完成的请求”上。

根据 Little 定律，并发数等于到达率乘以平均延迟。延迟一旦因为排队而上升，同样的到达率会占用更多并发资源；资源耗尽后，新请求连排队的机会都没有。限流和过载保护的作用，是在拐点之前主动丢掉一部分请求，让系统留在高吞吐区间。

重点系统不是被请求压死的，是被排队和重试拖死的。限流是为了保住大多数人。

知道系统怎么被压垮接下来决定在哪些层挡。看分层限流

限流要分几层

限流不是某个开关，是一层层卸力。

限流要发生在客户端、负载设备、网关、应用系统等多个节点；算法核心是漏桶和令牌桶。最终目的只有一个：减轻后端服务与数据库的压力。

倒金字塔的含义是：越靠近用户，越适合做粗粒度拦截；越靠近数据层，越要保护。客户端可以挡掉误触和重复点击，负载层可以按 IP 或连接数限速，网关可以按服务、接口、用户和租户限流，服务内部再用信号量或并发上限保护关键资源。

客户端层验证码 · 禁用按钮 · 调用限制 · 假排队
负载层Nginx / LVS / HAProxy 限速与连接数
服务层网关按服务、接口、用户、IP 限流
数据层最后一道防线，绝不能被打垮

倒金字塔限流

越往上，越适合挡流量

越靠近上层，事务处理压力越小，应对高并发的能力越强；越靠近底层，处理事务的能力越强，反而越怕被压垮。

因此流量应自上而下逐层递减：客户端先行拦截，负载层削峰，服务层按业务规则限制，数据层仅承接剩余流量。

从最外层开始客户端能先挡一部分。看客户端手段

最便宜的限流，在客户端

最便宜的限流，在用户点按钮的那只手上。

大多数用户不会主动发起服务攻击。客户端限流主要针对高频操作与误触，投入低、见效快。

纯前端验证码

请求过于频繁时弹出图片验证码，打断操作，区分人为还是机器。可由 JavaScript 前端生成，不需要考虑安全性。

禁用按钮

点击后立即禁用，直到收到服务端应答，防止用户因急躁反复点击造成重复请求。

调用限制

限制用户 1 秒内可发起的请求次数，超出时提示“您的操作过于频繁，请少安毋躁”。

假排队

提示“当前繁忙，正在排队 1/10 人”或“预计等待 5 秒”，人数和秒数随机，把请求摊开，减少同一时刻的并发。

重点客户端限流便宜好用，但只能挡住一部分。别指望它解决全部问题。

客户端挡不住的得靠算法。比较四种算法

四种算法，四种脾气

漏桶、令牌桶、滑动窗口，各有各的脾气。

限流算法要回答两个问题：允不允许突发？超出的请求是排队还是拒绝？漏桶和令牌桶给出两种典型答案；固定窗口和滑动窗口则决定了计数的时间边界。

漏桶 / 令牌桶模拟器 RATE LIMIT
通过0
排队中0
拒绝0
队列 0 / 10
下游服务固定速率流出

漏桶算法：请求进入队列排队，桶满后拒绝；下游按固定速率取走请求。突发流量会被削平，代价是排队等待。

四种计数方式的差别

常见限流算法的取舍
算法突发处理实现成本典型问题
固定窗口窗口边界可能出现双倍突刺低临界点流量翻倍
滑动窗口较平滑，可近似或精确中需要保存更多计数状态
漏桶削成固定速率，超出排队或拒绝中突发被延迟，队列可能积压
令牌桶允许一次性消耗积累令牌中突发过大时仍需下游保护

固定窗口实现最简单，但在窗口切换的瞬间可能放过接近两倍的流量；滑动窗口把时间切成更细的格子，按最近一段时间的总量判断，边界更平滑。漏桶把请求排队，以固定速率放行，适合保护下游数据库；令牌桶按固定速率补充令牌，允许请求在桶容量范围内突发，适合有明显峰谷的互联网流量。

实际系统常把两者组合：入口用令牌桶吸收突发，下游用漏桶或并发上限保护数据库。算法只是工具，关键是限流阈值要来自容量评估和压测，而不是拍脑袋。

重点漏桶把突发磨平，令牌桶让突发先过。选哪个，看你的下游怕不怕尖峰。

单机限流管不住总量多台机器要共享配额。看分布式限流

多台机器，怎么共用一个额度

一台机器限流容易，难的是十台机器一起说：总共只放这么多。

单机限流只能保证“每个实例不超过 N”，实例扩容后总配额会线性放大。要控制全局流量，需要把计数放到共享存储里，或者采用“本地预取 + 全局配额”的两级结构。

常见做法是用 Redis + Lua 实现原子令牌桶：Lua 脚本在 Redis 内部完成读取、补充、扣减和写回，避免并发竞态。缺点是每次限流都要访问 Redis，增加了延迟和 Redis 的负载；因此通常让每个实例先在本地预取一小批令牌，用完再向全局申请，以少量精度换取性能。

分布式限流的几种实现
方式精度性能适用场景
单机限流低（总配额随实例数放大）最高只保护单实例，不控制全局
中心化 Redis高受 Redis 延迟限制全局配额、严格限流
本地预取 + 全局配额中（有少量超发）较高大规模网关、兼顾性能与总量
一致性哈希分片计数中高按 key 分散计数，减少热点

重点单机限流管不住总量，多机就要共享配额。Redis 挂了是放行还是拒绝，得提前想好。

配额定了入口层负责执行。看 Nginx 和网关

入口层怎么执行限流

到了 Nginx 和网关这一层，限流才开始按业务说话。

服务端限流：Nginx 两个模块

ngx_http_limit_req_module 控制请求速率，ngx_http_limit_conn_module 控制连接数。负载设备是流量入口，最适合在这里先削一层。

limit_req_zone $binary_remote_addr zone=req:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;

server {
    limit_req zone=req burst=20 nodelay;
    limit_conn conn 20;
}

网关限流：按业务维度细分

用户、订单、库存微服务面临的压力不同，可以只针对订单服务限流，甚至只针对某个接口、某个用户、某个 IP、某个时间段限流。

灵活度高，是微服务架构里最常用的一层精细限流。配合客户端的粗粒度拦截和 Nginx 的入口限速，形成完整的倒金字塔。

分层顺序

客户端拦截 → 入口削峰 → 网关按业务限流 → 数据层承接剩余流量。

重点入口层解决的是“在门口挡多少”，更细的业务规则交给网关。

限流之外还得防止慢依赖把系统拖垮。补上组合拳

限流之外，还得有几手准备

限流只能决定放多少人进来，救不了已经被慢依赖拖住的系统。

限流决定“放多少请求进来”，但不能解决所有过载问题：下游变慢、依赖故障、重试放大、线程池耗尽，仍会把系统拖垮。完整的过载保护需要一组机制协同工作：超时、重试预算、熔断、舱壁、背压和降级。

TIMEOUT

超时

给每个下游调用设置上限，避免线程无限等待。超时应小于上游的超时，形成逐层收敛。

RETRY BUDGET

重试预算

只重试幂等请求，使用指数退避和抖动，并限制重试总量，避免把故障放大。

CIRCUIT BREAKER

熔断

错误率超过阈值时快速失败，给下游恢复时间；半开状态用于探测是否恢复。

BULKHEAD

舱壁

按依赖隔离线程池、连接池和队列，一个慢依赖不会耗尽所有资源。

BACKPRESSURE

背压

队列满时向上游反馈，而不是无限堆积；有界队列比无界队列更安全。

DEGRADATION

降级

关闭非核心功能、返回缓存或默认值，把资源留给登录、下单等核心路径。

过载保护机制的职责
机制防什么代价
限流总请求量超过容量部分用户被拒绝
超时线程被慢调用占死可能误杀慢但成功的请求
重试预算重试放大故障部分可恢复请求被放弃
熔断持续调用故障依赖恢复探测期间仍会失败
舱壁一个依赖耗尽全部资源资源利用率下降
降级核心功能被非核心拖垮用户体验不完整

重点限流只控制进入量，替代不了超时、熔断、舱壁和降级。
