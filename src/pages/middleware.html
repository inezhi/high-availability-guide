中间件高可用：四种系统的同一道题

一笔订单看起来只是一次点击，背后却要经过缓存、商品库、订单库和消息队列。四种系统，四种脾气。这一章，我们跟着这笔订单走一遍。

四种系统，其实在解同一道题

在跟着订单走之前，先把四种系统的共同骨架抽出来。

几乎所有高可用中间件都可以拆成四个动作：把数据复制到多个节点；持续检测节点是否存活；在旧主失效后选出一个新主；让客户端把请求发到新主。不同产品的差异，主要在于复制单位有多大、选举由谁主持、客户端如何感知拓扑变化。

四种中间件的高可用对照
系统复制单位故障转移一致性旋钮主要风险
Redis主从节点 / 哈希槽哨兵或集群自动切换复制是异步的；WAIT / min-replicas故障时丢最后一段写；脑裂

重点看中间件高可用，先问四件事：复制什么、谁选主、客户端怎么找新主、会丢多少数据。

先跟着用户打开商品页，第一站是缓存。看 Redis

Redis：内存存储、持久化与缓存失效

用户打开商品页，最先接住他的通常是缓存。

数据全在内存里，读写性能远超关系型数据库，通常作为缓存减少数据库访问和磁盘读写。高可用之外，先要照顾持久化和缓存失效。

Redis 的高可用可以拆成两个问题：数据不能全丢（持久化），服务不能停（主从、哨兵、集群）。两者目标不同，配置也经常需要权衡。

持久化：RDB 与 AOF

RDB

周期性快照。主进程 fork 子进程备份，对性能影响较低，恢复和重启更快。缺点是丢数据：5 分钟备份一次，宕机最多丢 5 分钟。

AOF

每条命令记日志。回放恢复，文件会变大，需要重写合并重复命令；恢复速度不如 RDB。

always

每次写完立即 fsync。最稳，一般不用。

no

交给操作系统调度。性能最好，丢失风险最高且不可控。

everysec推荐

每秒 fsync，最多丢最近 1 秒。

缓存失效的三种典型场景

雪崩

大规模缓存同时失效，大量请求直接打数据库。

延伸：过期时间打散、多级缓存

击穿

某个热点缓存失效，大量请求全打数据库。

延伸：互斥锁、逻辑过期

穿透

请求查缓存里根本没有的数据，直接越过缓存打数据库。

延伸：布隆过滤器、缓存空值

Redis 的三种高可用架构

主从

基础

一主一从、一主多从、主从从。主库读写，从库备份或分担读。同步分三种：全量同步（SYNC → fork 生成 RDB → 缓存期间的写 → 发送 → 从库加载）、增量同步（把缓存的写指令发给从库）、部分同步（断联后 PSYNC 从上次位置续传）。不能自动故障切换，必须手动把从改为主。

哨兵

自动转移

在主从基础上增加哨兵节点，组成“仲裁委员会”。哨兵不存业务数据；每 10 秒向主节点发 info 获取拓扑，每秒 ping 主、从和其他哨兵。单个哨兵判断是主观下线；超过半数哨兵认为不可用，才是客观下线。随后选举领头哨兵，把一个从节点（ID 较小）升级为主，其他从节点指向新主，并通知客户端。原主恢复后自动变从。本质是高可用读写分离：只有主节点对外读写。

集群

海量数据

分布式系统，每个节点存部分数据；多主多从，主故障时从节点被选举为主。固定 16384 个哈希槽，每个节点管理一部分。适合海量数据、高并发、高可用；数据量不大没必要上集群。

断联重连时用 PSYNC 从上次偏移量继续（部分同步），不必每次都全量复制。

哨兵与集群的边界

Redis 三种高可用架构的选择
架构数据分布故障转移适用规模
主从每个节点全量数据手动小规模、可接受人工切换
哨兵每个节点全量数据自动，多数哨兵判定数据量能装进单机内存
集群16384 个哈希槽分片自动，主节点故障后从节点提升海量数据、高并发

哨兵和集群都解决了自动切换，但都没有把 Redis 的异步复制变成强一致。主节点故障时，尚未复制到从节点的写入仍可能丢失。对数据敏感的场景，可以开启 min-replicas-to-write，要求至少有一个从节点在线且复制延迟不超过阈值时才允许写入；代价是牺牲一部分可用性。

缓存侧还要区分三类问题：雪崩是大面积失效，击穿是单个热点失效，穿透是查询根本不存在的数据。它们对应的治理手段不同：雪崩用过期时间打散和多级缓存，击穿用互斥锁或逻辑过期，穿透用布隆过滤器和空值缓存。

重点Redis 快，但异步复制会丢最后一段；哨兵能切换，不等于零丢失。

缓存没命中请求落到商品库。看 MongoDB

MongoDB：副本集与分片

缓存没命中，商品详情总得有个地方落下来。

副本集解决单节点故障：多数节点存活，即可选举出新的主节点。分片解决单机容量：数据按分片键分布到多个 shard，每个 shard 本身又是一个副本集。两者叠加，才能同时获得故障转移和水平扩展能力。

主从

已废弃 · 不推荐

用法一：从库只做实时备份，不干活。用法二：读写分离，从库只读。没有故障转移，宕机必须手动切库，应用还得改连接信息。

副本集

推荐

选举出 master 负责读写，其他副本承担备份和读操作；节点间心跳判定可用；每个节点都保存全量数据。

分片

水平扩展

三个角色：shard、router、config servers。只对部分集合分片；未分片的集合必须放在主分片；分片键选中后不能改。

分片算法

选键之后不可改
HASH

RANGE

写关注与读偏好：一致性由客户端选择

MongoDB 把一致性的一部分控制权交给了客户端。写关注（write concern）决定一次写入需要多少个节点确认才返回；读偏好（read preference）决定查询发给主节点、从节点还是最近节点。两者组合，可以在延迟与一致性之间做细粒度权衡。

w:1 只等主节点确认，写入最快，但主节点故障时可能丢失尚未复制到从节点的数据；w:majority 等待多数节点确认，故障时更安全，但写入延迟更高。读偏好设为从节点可以分担读压力，却可能读到旧数据，适合对实时性要求不高的查询。

分片键的选择
类型优点风险适合
Hash 分片分布均匀，写入分散范围查询要扫多个分片按用户 ID 随机读写
Range 分片范围查询高效末尾分片容易成为热点时间序列、按区间查询
复合分片键兼顾分布与查询设计复杂，选定后难改多租户、地域 + 用户

重点MongoDB 的一致性有一部分是客户端选的：w:1 快，w:majority 稳。

重点分片键选错，后面天天救火。它选定后基本不能改。

用户决定下单订单要落库。看 MySQL

MySQL：主从复制与一致性取舍

用户点下提交订单，这一刻才真正开始考验数据库。

主备、主从、互为主从解决读扩展和备份，真正的取舍在复制策略：等不等从库，等几个从库。

MySQL 的高可用主要围绕复制展开：主库把变更写入 binlog，从库拉取并回放。主备、主从、互为主从的区别，是复制拓扑和读写入口不同；异步、半同步、全同步的区别，是主库何时向客户端确认。

主备

备份

一个主库一个备库，主库实时同步到备库。备库不提供任何服务，长期闲置；主库故障不能自动转移，必须由 DBA 手动切换。

主从

读扩展

一主一从、一主多从、主从从。从库分担读压力，但主库的写压力并没有减轻。

互为主从

写扩展 · 复杂度高

两个节点都支持读写，数据相互同步，读写能力同时提高。难点是主键不能冲突，一旦数据不一致将很难恢复。

策略客户端何时收到响应一致性风险 / 代价
异步复制MySQL 默认
主库提交事务后立即返回
0 个从库确认
响应最快；主库宕机时，未同步的数据会丢

异步复制下，如果主库在数据到达从库前宕机，切到从库就会缺一段数据；这是拿一致性换响应速度的典型交易。

GTID 与故障转移工具

传统基于 binlog 文件名的复制，在切换时需要精确计算从库执行到了哪个位置，容易出错。GTID（全局事务标识）给每个事务一个唯一编号，从库可以自动定位已执行的事务，大幅简化主从切换和故障恢复。

复制本身不提供自动故障转移。生产环境常用 MHA、Orchestrator、MySQL Group Replication / InnoDB Cluster 或云数据库的托管切换。选型时要关注：能否自动选主、能否保证数据不丢、切换期间是否只读、客户端如何重连。

MySQL 常见高可用方案
方案故障转移数据一致性适用场景
主备 + MHA / Orchestrator外部工具自动或半自动取决于复制策略，可能丢最后一段传统主从架构、可控运维

重点MySQL 的复制策略就是一道选择题：快、稳、还是折中。复制策略也不等于自动故障转移。

订单落库后还得通知库存和物流。看 Kafka

Kafka：分区副本撑起高可用

订单落库不等于结束。库存、物流、积分都还在等消息。

消息先进入分区，分区有 Leader 和 Follower 副本；Leader 故障，Follower 被选举上位。高可用发生在“分区”这一级，而不是整台 Broker。

Kafka 的高可用单位是分区，而不是 Broker。每个分区有一个 Leader 和若干 Follower；生产者只写 Leader，Follower 持续拉取复制。Leader 故障后，集群从同步副本中选举新的 Leader，分区继续可写。

POINT-TO-POINT

点对点

生产者把消息发到队列，多个消费者监听，但一条消息只有一个消费者能消费。

PUB / SUB

订阅

生产者把消息发到主题，订阅了这个主题的消费者都能收到。

  • 集群借助 ZooKeeper 存节点元数据，实现 Broker 高可用；新版 Kafka 也支持不依赖 ZooKeeper 的 KRaft 模式。
  • 每个主题划分多个分区，消息按算法分配到不同分区；分区不可用会丢数据，所以用分区副本兜底。
  • 生产者写 Leader 副本，Leader 同步给 Follower；Leader 故障，选举一个 Follower 升为 Leader。

ISR 与 acks：可靠性由生产者与主题共同决定

Kafka 把“追得上 Leader 的副本”称为 ISR（In-Sync Replicas）。生产者设置 acks=all 时，Leader 会等待 ISR 中的副本确认；主题设置 min.insync.replicas 时，只有 ISR 数量达到下限才接受写入。两者配合，才能在 Broker 故障时尽量不丢消息。

如果允许“非同步副本”被选为 Leader（unclean leader election），分区可以更快恢复可用，但可能丢失未同步的消息。大多数业务应关闭该选项，让分区在 ISR 不足时短暂不可用，而不是悄悄丢数据。

消费者侧的高可用由消费组负责：分区在消费者之间分配，某个消费者退出会触发 rebalance。rebalance 期间消费会短暂停顿，因此要避免频繁扩缩容和长时间处理单条消息；必要时可以用静态成员或增量协作协议减少抖动。

重点Kafka 的高可用单位是分区，不是 Broker。Leader 挂了，得看同步副本接不接得上。

重点acks 和 ISR 才决定会不会丢消息；允许非同步副本选主，能用，但可能丢。

走完一笔订单，再回看选型

走完一笔订单再选型，会容易得多。

四种系统的高可用机制不同，但选型不应从“哪个切换最快”开始。先看数据模型和访问模式：需要事务和复杂查询，选 MySQL；需要文档结构和灵活 schema，选 MongoDB；需要极低延迟的缓存，选 Redis；需要高吞吐消息和解耦，选 Kafka。高可用是在选定系统之后，按业务对 RPO / RTO 的要求配置的。

同一个系统也可以有不同的高可用级别：Redis 主从、哨兵、集群对应不同规模；MySQL 主备、半同步、组复制对应不同一致性要求。不要为了“看起来高可用”而直接上最复杂的一套，复杂度本身就是故障来源。

按业务目标选择高可用级别
业务要求建议需要接受的代价
能接受分钟级中断，数据可重放主从 + 备份，人工切换恢复慢，依赖值班
要求自动切换，能接受少量丢失异步复制 + 自动选主故障瞬间可能丢最后一段
要求自动切换且尽量不丢半同步 / 多数派确认写入延迟增加，容量下降
要求跨机房持续可用多副本 + 单元化 / 多活成本高，冲突解决复杂

重点走完一笔订单，选型就没那么抽象了：先看数据模型，再看高可用。
