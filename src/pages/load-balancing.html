第 03 章 · 入口

负载均衡：把流量分给健康的节点

负载均衡同时承担两件事：把请求分摊到多个节点，以及在节点故障时把流量移走。它既是水平扩展的入口，也是高可用的第一道闸门。但负载均衡器自己也会故障，因此入口层必须像它保护的后端一样被保护。

阅读约 16 分钟 关键词：健康检查 · 调度算法 · L4 / L7 · 一致性哈希 · GSLB
本章要点
  • 负载均衡同时解决容量和故障：分发请求，并把故障节点从列表中摘除。
  • 调度算法没有绝对优劣，取决于服务是否有状态、节点是否同构、流量是否可预测。
  • 四层转发快，七层能力多；多级负载把两者叠加，才能同时获得吞吐与灵活度。
  • DNS 轮询没有健康检查，不能独立完成故障转移；入口层自身必须做双机或多级冗余。

负载均衡的两个职责

从流量方向看，负载均衡可以分成南北向和东西向：南北向面对客户端进入数据中心的流量，通常由 F5、LVS、Nginx、云负载均衡承担；东西向面对服务之间的调用，常见于服务网格和内部网关。两者的算法相似，但故障域、性能要求和运维方式不同。

HARDWARE

硬负载

F5、Radware 等专用设备。性能强、稳定性高，但成本高、扩展灵活性有限。

SOFTWARE

软负载

Nginx、LVS、HAProxy 等软件。成本低、部署灵活，是大多数系统的默认选择。

负载均衡位于客户端与后端服务之间，一方面把请求分摊到多个节点，另一方面通过健康检查把故障节点从转发列表中移除。它同时解决“单节点容量有限”和“单节点故障”两个问题，但自身也成为新的单点，因此需要双机主备或多级冗余。

按工作层次，负载均衡分为四层和七层：四层只看 IP 与端口，转发开销小；七层能解析 HTTP，按 URL、Header 路由，适合灰度、改写和细粒度限流。层次越高，能力越强，性能开销也越大。

重点负载均衡同时解决“容量不足”和“单节点故障”，但它自身也是新的单点；入口层必须做双机主备或多级冗余。

健康检查：只把流量给能服务的节点

健康检查是负载均衡的前提。没有健康检查，负载均衡只是按公式分配请求，无法知道节点是否真的能服务。主动检查由负载均衡器定时发起，适合发现进程退出、端口不可达；被动检查根据真实请求的失败率判断，适合发现业务逻辑异常。两者通常一起使用。

检查参数需要配合业务：间隔太短会增加探测压力，太长会延长故障发现时间；超时和连续失败次数决定误判概率。对于有状态服务，还要区分“进程活着”和“可以接流量”——数据库复制延迟过高、缓存尚未预热、依赖未就绪，都应该被视为不健康。

健康检查的常见参数与取舍

重点健康检查要回答“这个节点现在能不能接业务”，而不只是“端口通不通”。阈值和恢复策略决定故障发现速度与误判率，必须结合业务延迟一起调。

    入口层自身的高可用

    负载均衡器自身是流量入口，一旦不可用，后端再健康也无法访问。常见的做法是双机主备：两台 Nginx 通过 Keepalived 绑定同一个 VIP，由 VRRP 决定谁持有 VIP；主节点故障时，备节点在数秒内接管 VIP。需要注意，VIP 漂移只解决入口故障，不能提升单机 Nginx 的连接数上限，因此高并发场景还需要多级负载。

    多级负载把不同层次的设备串联起来：硬负载负责最外层的高吞吐，LVS/HAProxy 做四层转发，Nginx 做七层路由与应用层能力。每一层都可以用 Keepalived 做成主备，从而避免任何单台设备成为整条链路的单点。

    Nginx + Keepalived 双机主备

    • 两台 Nginx 各自独立 IP，都装 Keepalived，并绑定同一个虚拟 IP。
    • 主节点存活时流量走主；主宕机后 VIP 自动漂移到备节点，完成故障转移。
    • 原主恢复后自动变成备机。两台 Nginx 的配置必须时刻完全一致。
    • 缺点：同一时间只有一台对外服务，单机连接数有限，Nginx 本身无法水平扩展。

    重点Keepalived 只能解决入口设备的单点，不能提升单机连接数上限；高并发场景需要 LVS / HAProxy + Nginx 的多级结构，并让每一层都具备冗余。

    四层与七层：能力与开销的取舍

    四层负载

    传输层 · TCP / UDP

    只看 IP 和端口，转发快、开销小。代表：LVS、HAProxy、F5。

    七层负载

    应用层 · HTTP / HTTPS

    能读 URL、Header，做路由、改写、限流。代表：Nginx。新版 Nginx 也可用 stream 模块做四层。

    重点四层只读取 IP 与端口，转发快；七层能解析 HTTP，能力灵活但开销更大。多级负载把两者叠加，才能同时获得高吞吐与水平扩展。

    调度算法：每种策略都带着假设

    负载策略

    常见负载策略及其适用假设

    轮询

    按顺序轮流分配，简单均匀。

    权重轮询

    能力强的节点多接，按权重比例分配。

    动态权重轮询

    根据 CPU、内存、IO 算权重，让空闲的节点多接。

    最小连接数

    每次给当前连接数最少的机器。

    最短响应

    发给响应时间最快的服务器。

    IP 哈希

    同一来源固定落到同一节点，用来保 session。

    URL 哈希

    同一类 URL 固定落到同一节点，便于缓存。

    最小会话

    优先选择当前会话数最少的节点。

    趋势分析

    按请求变化趋势提前调度，适合可预测的流量。

    随机

    随机挑一台；量大时趋近均匀，短窗口会抖动。

    选择策略时先回答三个问题：服务是否有状态、节点能力是否一致、流量是否可预测。无状态且节点同构，轮询或随机即可；节点异构，用加权或最少连接；需要会话保持，用 IP 哈希；流量有明显趋势，可用趋势分析。会话保持会带来一个副作用：节点扩缩容时映射变化，部分会话会失效，因此更稳妥的做法是把会话状态外置到共享存储。

    调度算法没有绝对优劣，取决于服务形态与节点差异。无状态且节点同构时，轮询或随机即可；节点能力不同时，用加权轮询或最少连接；需要会话保持时用 IP 哈希；流量有明显趋势时，可用趋势分析提前调度。任何策略都必须配合健康检查，否则只会把请求分给已经故障的节点。

    还有两个常被忽略的策略：最少响应时间按历史响应时间选择最快的节点，适合节点性能差异明显且请求耗时稳定的场景；Power of Two Choices 随机选两个节点，再把请求给其中连接数较少的那个，以很小的采样成本获得接近“最少连接”的效果，在大规模集群中很常见。

    重点选择策略时先回答三个问题：服务是否有状态、节点能力是否一致、流量是否可预测。策略越“聪明”，对指标和调参的依赖越强。

    全局负载：DNS、GSLB 与 Anycast

    DNS 轮询

    DNS 轮询：最外层的负载分担

    域名绑定多个 IP，DNS 按顺序依次返回，用户请求被分配到不同地址，服务因此可以水平扩展。

    但它有两个明显限制：服务器直接暴露在互联网上；吞吐依然不足。更常见的是 DNS + 多级负载——域名解析到 LVS 的 VIP，再由 LVS 和 Nginx 分发，后端不暴露。

    没有健康检查

    DNS 没有主动探测机制。某个节点宕机，DNS 不会自动把它的 IP 从列表里摘掉，用户仍会被解析到坏节点。DNS 轮询做不到自动故障转移。

    图示：DNS 按顺序返回三个 IP，其中 IP 3 已宕机但仍会被返回。

    重点DNS 轮询没有健康检查，节点宕机后坏 IP 不会被自动摘除，因此 DNS 轮询不能独立完成故障转移。

    DNS 轮询是最简单的全局负载：域名绑定多个 IP，解析时按顺序返回。它能把用户分配到不同机房，但 DNS 没有健康探测，节点宕机后坏 IP 仍可能留在解析结果里；TTL 缓存还会让切换延迟从几秒到几十分钟不等。

    更完整的方案是 GSLB（全局服务器负载均衡）：由权威 DNS 根据用户地理位置、运营商、机房健康状态和容量返回不同地址。它本质上把“健康检查 + 就近接入”放在了解析层。Anycast 则让多个机房宣告同一个 IP，由网络路由把用户带到最近或最健康的入口，常用于 DNS、CDN 和 DDoS 清洗。

    重点DNS 轮询没有健康检查，节点宕机后坏 IP 不会被自动摘除，因此 DNS 轮询不能独立完成故障转移。GSLB 把健康检查带入解析层，但仍要受 DNS 缓存 TTL 约束。

    会话保持与一致性哈希

    需要会话保持时，IP 哈希可以让同一来源固定落到同一节点。但普通取模哈希在节点增减时会把几乎所有 key 重新映射，导致缓存大面积失效、会话集中掉线。一致性哈希把节点和 key 映射到同一个环上，节点变化时只影响相邻区间，迁移量大幅减少。

    一致性哈希并不能消除热点：如果 key 分布不均，某个节点仍可能承担过多请求。工程上通常引入虚拟节点，让每个物理节点在环上出现多次，使分布更均匀。即使如此，热点 key 仍需要单独处理，例如本地缓存、key 拆分或请求合并。

    重点会话保持会带来副作用：节点扩缩容时映射变化，部分会话会失效。更稳妥的做法是把会话状态外置到 Redis 等共享存储，而不是依赖 IP 哈希。

    01

    健康检查是否覆盖真实业务路径？失败阈值和恢复阈值是否调过？
